The RentCast property schema documents ID, formatted address and `addressLine2` unit, coordinates, type, beds/baths, living/lot area, year built, last sale date/price, sale history, and owner details. It does not establish photos, current listing status/asking price, or an assigned-school contract for this project. The runner reports field presence/type for these candidates on an unambiguous sample and drops owner/contact data before normalization or reporting. A single absent field will not be treated as globally unsupported. Sale-listing `price` is an ask, distinct from property `lastSalePrice`. Inactive listing data is not a recorded transaction.

Milestone 03 uses the documented [address search query](https://developers.rentcast.io/reference/property-records) and validates one exact subject before persistence. The normalized payload is a strict allowlist of property-record address and structural fields from the [property data schema](https://developers.rentcast.io/reference/property-data-schema), including `addressLine2` for unit identity and `squareFootage`/`lotSize` for area. Owner and unrelated response fields are discarded before storage. `currentListPrice` remains null because this property-record response does not establish an active asking price. The adapter and cache have been tested with mock responses; subsequent sample-specific live school verification is recorded below.

Milestone 04 adds two bounded geographic requests, one to records using `saleDateRange` and one to sale listings using `status=Active`. The response allowlist excludes owners and listing contacts. Records missing a usable sale price or date are not presented as recorded-sale evidence. Listings retain asking-price semantics, including when an ask is unavailable. A mocked browser subject at Austin coordinates was used solely to verify ArcGIS rendering and the existing frontend key at the documented localhost referrer. This did not save a property or call RentCast. No other referrer was tested, and no claim is made about live market-data coverage.

**Assigned-school dependency:** The checked property schema does not document a verified attendance-assignment field. The smoke runner can distinguish no school field, a school-related field of unverified meaning, and an `assignedSchools` array shape if observed; none alone proves an authoritative assignment. Milestone 05 implements the unavailable response and UI. Its future assignment source determines **which** school is assigned; a separate metadata source may enrich only those identities. A reference dataset or nearest-school search cannot create an assignment. CDE ingestion was not needed or attempted. Never infer assignment from proximity or an LLM.

ArcGIS Places requires a separate server credential with Places privilege. The Milestone 05 endpoint resolves exact Grocery Store/Supermarket categories with one categories request and performs at most one near-point request per selection. It normalizes only display fields in memory; `Cache-Control: no-store` and context-off state clearing avoid a persistent result cache. Esri states that Places may not be permanently stored; no Places records go to PostgreSQL, fixtures, snapshots, logs, docs, or OpenAI. The browser key is basemap-only and is never used for Places. Mocked tests validate request shape and status handling; live server key privilege and live grocery coverage are **NOT RUN**.

CAL FIRE describes [Fire Hazard Severity Zones](https://osfm.fire.ca.gov/what-we-do/community-wildfire-preparedness-and-mitigation/fire-hazard-severity-zones) as hazard designations, distinct from property-specific wildfire risk. The SRA 2024 layer is effective; the 2025 LRA layer provides recommendations for local adoption. The subject query first resolves responsibility area, then checks the appropriate zone polygon. The client requests polygons for the current viewport only and does not save source features. `NonWildland` at the live City Hall point is mapped to “outside the currently displayed hazard zone,” never “safe.”

The CGS service is the mapped Quaternary fault **trace** layer. Its `FLT_NAME` is a mapped feature name, and the server computes an approximate point-to-line-segment distance from returned geometry within a 20-mile search. The 2010 map's 1:750,000 scale and mapped line meaning limit parcel-level interpretation. The browser displays the official line geometry only while Faults is selected. Neither hazard source is used for pricing, and neither is a substitute for engineering, insurance, or regulatory review.

The Milestone 01 smoke check originally documented `gpt-6-luna` and `low`. Milestone 08 changed the application and smoke configuration default to `gpt-5.6-luna` and `low`; existing ignored local configuration still takes precedence. One tiny synthetic smoke request has `store:false`, no tools, max 800 output tokens, an 8-second timeout, and SDK retries disabled. No fallback model or repair request is attempted. Actual usage is recorded only when returned. Authentication, permission, rate-limit, unsupported configuration, refusal, incomplete output, timeout, and malformed output remain distinct outcomes. The separate Milestone 08 analysis adapter and synthetic evaluation are documented in [AI analysis](ai-analysis.md).

## Assigned-school investigation — 2026-10-01

### 1. Root Cause

All properties used `UnavailableAssignmentSource`, wired in `server/src/index.ts`; it made no school-provider request and always returned null. The UI also treated `PROVIDER_ERROR` as a successful empty assignment result. These were implementation/state-semantics defects. Separately, the reported property's actual RentCast response contains no school data; there is no lost assignment to restore for that sample.

### 2. Evidence

For the user-provided address `2634 E Scarlett Ln, Ontario, CA 91762`, the saved PPI profile was inspected first. `DataSnapshot.normalizedPayload` contains the structural/address allowlist only; it is not a raw response archive. No saved raw record or development log was found in the repository. One explicitly gated diagnostic then used the existing `RentCastPropertyProvider` with an observing transport: `GET /v1/properties`, query `address` plus `limit=10`, API v1. It made exactly one attempt, with no retries, fallback, or database writes.

At `2026-10-01T15:49:49.504Z`, the response was HTTP 200, an array of one record, with one address match. The observer traversed all 78 object fields recursively before normalization. No key contained school, district, attendance, or boundary terminology; this included nested objects and arrays. All top-level branches were inspected: address/identity/FIPS/county/coordinates, structural attributes, assessor/legal fields, last-sale fields, HOA, features, taxAssessments, propertyTaxes, history, owner, and ownerOccupied. Nested features, historical/tax entries, and owner/mailing-address objects likewise contained no assignment, school-district, or nearby-school fields. Only field names/types/counts were retained; raw values were neither printed nor stored.

The current [property schema](https://developers.rentcast.io/reference/property-data-schema), [endpoint parameters](https://developers.rentcast.io/reference/property-records), and [official API index](https://developers.rentcast.io/llms.txt) document no school assignment/district/nearby-school contract, school include parameter, or separate school endpoint. `features.viewType` can have the enum value School; that describes a view, not attendance assignment. This conclusion concerns the observed response and current public API contract, not a claim about every future/private RentCast product.

### 3. Data Flow Before Fix

Property: Dashboard search → `resolveProperty` → `/properties/resolve` → property service → RentCast `/v1/properties` → passthrough raw validation → explicit normalized allowlist → PPI Property/DataSnapshot → property envelope → frontend shared schema → subject summary. School data was absent in the raw sample before any transformation. Normalization does discard unrelated fields, but did not discard an existing assignment in this sample. No school columns or school snapshot/cache exist; JSON serialization is not the cause.

Schools: Schools click → Dashboard on-demand effect → `getAssignedSchools` → `/properties/:id/assigned-schools` → saved subject lookup → permanently empty production source → `ASSIGNMENT_UNAVAILABLE` → shared/client parsing → ContextPanel. ArcGIS school markers are derived only from verified assignments, not radius queries. The property ID, request cancellation, and selected-context checks prevent obsolete responses from rendering. One mismatch previously left the UI loading; it now fails explicitly.

### 4. Changes Made

Separated source-not-connected from a successful empty result; added runtime validation at the assignment adapter boundary; returned distinct sanitized 502 errors for upstream failure versus malformed payload; classified invalid frontend JSON/schema and mismatched property IDs; fixed the legacy `PROVIDER_ERROR` UI branch. Existing backend error logging records fixed code and request ID only. No new provider, database schema, raw record persistence, school assignment inference, or geographic school substitution was added.

### 5. Data Flow After Fix

Production source not connected → `SOURCE_UNAVAILABLE` → “School assignments not connected.” Successful null/empty adapter result → `ASSIGNMENT_UNAVAILABLE` → genuine empty message. Failed request → `502 SCHOOL_ASSIGNMENT_PROVIDER_ERROR` → “School request failed.” Invalid adapter result → `502 SCHOOL_ASSIGNMENT_PROVIDER_MALFORMED`; invalid API JSON/schema/identity → client error → “School response invalid.” Valid verified adapter result → normalization/enrichment → HTTP JSON → frontend schema → school list and resolved markers. Loading remains separately visible.

### 6. Tests / Verification

Backend regressions cover valid identities/enrichment, successful empty responses, source not connected, malformed objects/arrays/fields/coordinates, HTTP serialization, distinct 502 responses, and sanitized logs. Frontend regressions cover the service-generated synthetic success response, loading, empty/source/error/parse states, wrong-property response, and late assignment response after a subject switch. The synthetic verified adapter is explicitly an internal contract fixture; it is not presented as RentCast's schema. The ordinary suite passed 169 tests before the subsequent 09.1 map refinement (five separately gated database tests skipped); typecheck and lint passed. The real reported property was subsequently checked in the browser: its Schools panel shows the source-not-connected explanation and leaves the real basemap usable.

### 7. RentCast Limitation, if any

The inspected public API supplies property records, including structural, tax, sale-history and owner fields, but no documented authoritative attendance assignment or school district field. This sample returned neither assigned schools, school district, nearby schools, nor radius-derived schools. Those four concepts remain distinct. No real successful assignment sample was identified; the success path was verified with a synthetic internal verified-source fixture.

### 8. Remaining Risks / Follow-ups

Real assigned-school functionality still requires a documented, authoritative property-specific attendance source. The smallest next step is to verify such a source and connect it through `VerifiedAssignmentSource`, including effective school year and address/grade semantics. No paid integration was added. One absent sample does not prove universal absence; revisit the adapter if the official contract changes. The old per-property empty state must not be interpreted as a verified statement that no schools are assigned.
