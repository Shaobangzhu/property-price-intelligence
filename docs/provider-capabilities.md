The RentCast property schema documents ID, formatted address and `addressLine2` unit, coordinates, type, beds/baths, living/lot area, year built, last sale date/price, sale history, and owner details. It does not establish photos, current listing status/asking price, or an assigned-school contract for this project. The runner reports field presence/type for these candidates on an unambiguous sample and drops owner/contact data before normalization or reporting. A single absent field will not be treated as globally unsupported. Sale-listing `price` is an ask, distinct from property `lastSalePrice`. Inactive listing data is not a recorded transaction.

Milestone 03 uses the documented [address search query](https://developers.rentcast.io/reference/property-records) and validates one exact subject before persistence. The normalized payload is a strict allowlist of property-record address and structural fields from the [property data schema](https://developers.rentcast.io/reference/property-data-schema), including `addressLine2` for unit identity and `squareFootage`/`lotSize` for area. Owner and unrelated response fields are discarded before storage. `currentListPrice` remains null because this property-record response does not establish an active asking price. The adapter and cache have been tested with mock responses; live RentCast verification remains **NOT RUN** because no explicit live address was supplied.

Milestone 04 adds two bounded geographic requests, one to records using `saleDateRange` and one to sale listings using `status=Active`. The response allowlist excludes owners and listing contacts. Records missing a usable sale price or date are not presented as recorded-sale evidence. Listings retain asking-price semantics, including when an ask is unavailable. A mocked browser subject at Austin coordinates was used solely to verify ArcGIS rendering and the existing frontend key at the documented localhost referrer. This did not save a property or call RentCast. No other referrer was tested, and no claim is made about live market-data coverage.

**Assigned-school dependency:** The checked property schema does not document a verified attendance-assignment field. The smoke runner can distinguish no school field, a school-related field of unverified meaning, and an `assignedSchools` array shape if observed; none alone proves an authoritative assignment. Milestone 05 implements the unavailable response and UI. Its future assignment source determines **which** school is assigned; a separate metadata source may enrich only those identities. A reference dataset or nearest-school search cannot create an assignment. CDE ingestion was not needed or attempted. Never infer assignment from proximity or an LLM.

ArcGIS Places requires a separate server credential with Places privilege. The Milestone 05 endpoint resolves exact Grocery Store/Supermarket categories with one categories request and performs at most one near-point request per selection. It normalizes only display fields in memory; `Cache-Control: no-store` and context-off state clearing avoid a persistent result cache. Esri states that Places may not be permanently stored; no Places records go to PostgreSQL, fixtures, snapshots, logs, docs, or OpenAI. The browser key is basemap-only and is never used for Places. Mocked tests validate request shape and status handling; live server key privilege and live grocery coverage are **NOT RUN**.

OpenAI defaults are configurable `gpt-6-luna` and `low`, both documented for the Responses API. One tiny synthetic structured-output request has `store:false`, no tools, max 800 output tokens, an 8-second timeout, and SDK retries disabled. No fallback model or repair request is attempted. Actual usage is recorded only when returned. Authentication, permission, rate-limit, unsupported configuration, refusal, incomplete output, timeout, and malformed output remain distinct outcomes.
