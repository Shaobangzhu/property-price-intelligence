# PPI architecture through Milestone 09

The browser is a Vite/React app with Dashboard and History routes. Express owns HTTP validation, CORS, security headers, request IDs, and safe errors. Shared Zod contracts define property API inputs and responses. Docker PostgreSQL is the sole supported local database in the existing `ppi-local` Compose project. Prisma 6.12.0 defines and migrates the schema; runtime persistence uses the existing `pg` pool. No separate PostgreSQL service or Prisma Client runtime was introduced.

## Property resolution

`POST /api/properties/resolve` validates a full address and normalizes a key that retains apartment or unit identity. `PropertyService` first reads the latest `PROPERTY_PROFILE` snapshot for a matching saved subject. It returns a cache hit only when `expiresAt` is later than now and no later refresh failure marked the profile stale. A missing, expired, or marked-stale profile causes one call through `PropertyDataProvider`; `RentCastPropertyProvider` is the production implementation. It uses a fixed endpoint, server-only key, eight-second timeout, no redirects or retries, and a bounded response size. Exact normalized address and unit matching must identify one subject. Empty, ambiguous, malformed, and upstream failures produce distinct safe API errors.

The adapter projects only documented, validated structural and address fields into `NormalizedProviderProperty`. This whitelist excludes owner names, mailing addresses, phone numbers, email, unrelated identities, tax/history blobs, and raw provider JSON. The property-record endpoint does not establish a verified current listing price, so `currentListPrice` stays null. No comparable, listing, school, Places, hazard, or AI data is fetched or persisted here.

The service waits for the remote response before opening a database transaction. The repository uses advisory transaction locks on normalized address and provider identity, uniqueness constraints for address key and provider ID, and a versioned snapshot insert. This protects simultaneous resolves and refreshes without holding a transaction through network latency. The browser aborts superseded searches and checks request identity before changing the selected property. In-process singleflight coalesces repeated requests for the same key.

Milestone 09 adds token-aware checks around the legacy concatenated address key. A collision returns `PROPERTY_IDENTITY_CONFLICT` instead of overwriting another subject. Refresh requires its original property ID to still exist; deleting a subject while its provider request is pending cannot recreate it. Pricing captures one validated subject envelope before requesting comparable evidence for that same subject. Untrusted browser Origins and cross-site requests without an Origin are rejected before provider routes. No-Origin CLI requests remain supported for local development.

Local origin configuration expands each validated origin to both `localhost` and `127.0.0.1` at the same scheme and port. This supports the Vite bind address and existing localhost configuration without changing user-owned env files. The request guard and CORS middleware receive the same expanded list. Other ports, remote domains, deceptive localhost subdomains, and opaque `null` origins remain forbidden.

## Data ownership and freshness

`Property` stores provider-normalized fields, subject-only identity, user notes, and JSONB override entries. A stable RentCast ID is preferred where available; a normalized full address including unit is also unique. `DataSnapshot` stores a sanitized normalized payload, hashes, `fetchedAt`, and `expiresAt`; its `PROPERTY_PROFILE` TTL is 14 days. `Property.updatedAt` records edits but never determines provider freshness. A failed refresh leaves the snapshot and fetched time unchanged and sets `refreshFailedAt`, so future reads show stale state until a successful provider fetch clears the marker. `STALE_FALLBACK` is explicit in resolve/refresh responses.

Notes and supported overrides (`bedrooms`, `bathrooms`, `livingAreaSqft`, `yearBuilt`) are user-owned. Each override stores its value, `USER` provenance, and edit timestamp. The API returns both the original provider field and `effectiveValues`; an override changes only the latter. PATCH cannot write provider fields or mutate snapshots. DELETE removes only the selected PPI subject property and cascades its PPI snapshots. Future comparable properties must not be inserted into subject History implicitly.

## Market evidence and map

`GET /api/properties/:id/market-context` loads a saved subject, then checks separate `RECORDED_SALES` and `ACTIVE_LISTINGS` snapshots. Their default application cache TTLs are seven days and 24 hours. `PROPERTY_PROFILE` remains 14 days by default and is configurable from 1–60 days. Server configuration bounds radius (0.1–10 miles), result limit (1–100), sale date range (1–1095 days), and the two market TTLs. Defaults are two miles, 25 results per endpoint, and 365 sale days. Query coordinates and bounds are stored beside the normalized candidates in each snapshot; a query hash prevents a policy or subject-coordinate change from using the old cache. Each provider request has one page, no offset, no retry, and an eight-second timeout. The two kinds refresh independently and return an explicit stale fallback when a provider request fails.

RentCast property records with a valid `lastSalePrice` and `lastSaleDate` become `RECORDED_SALE` candidates. RentCast sale listings are requested with `status=Active`, and only returned Active entries become `ACTIVE_ASKING_PRICE` candidates. Inactive asking prices and AVMs are not represented as sales. Missing optional structural fields, listing prices, dates, or coordinates are `null`, never zero. A candidate without coordinates remains in the table and has no marker. No candidate is inserted into `Property` or subject History. Snapshot and API payloads retain only an allowlist of fields, not raw provider responses, owners, or listing agents. The ID is stable across refreshes from evidence kind plus provider ID or normalized address. This is candidate retrieval, without pricing selection or valuation.

The reusable map component dynamically loads ArcGIS Maps SDK for JavaScript after mount, creates one `MapView` with separate subject, recorded-sale, active-listing, selected-context, and wildfire graphics layers, and destroys its view and event handlers on unmount. The subject layer is always visible and drawn above optional markers. Recorded Sales and Active Listings default off and have independent `GraphicsLayer.visible` controls; their complete evidence still feeds tables and analysis. Toggles retain the view, graphics, zoom, and pan. Core row and marker selection share the same candidate ID; selecting a hidden candidate from a table does not enable its map layer. The context layer has its own graphics and selection callback, so switching a context clears those graphics while keeping the view and core layers. The four context buttons are mutually exclusive and all can be off. Dashboard retains market and context preferences across property searches while replacing subject data. Wildfire geometry comes from bounded official CAL FIRE viewport queries and is drawn as classified polygons; the active CGS fault-trace `FeatureLayer` is added below core markers. Inactive government sources are removed. Overlay failure displays a small notice without hiding the core map. Popups contain only normalized facts. The frontend basemap key stays in `client/.env.local`; server Places credentials never enter Vite. A map load failure is isolated from the rest of Dashboard.

Dashboard aborts older subject, market, and context requests when a new search begins or a context changes. Responses must match the visible property ID and active context before rendering, so late A results cannot appear under subject B. The map is unmounted while the subject changes and never retains A's graphics with B's summary.

## Schools and Grocery context

Post-freeze scope revision (2026-10-14): the school feature now displays **Nearby Schools**, not attendance assignments. `NearbySchoolsService` loads the saved subject and passes its formatted address to a backend `ZillapiClient`. `createSchoolProvider` uses the validated legacy `SCHOOL_ASSIGNMENT_PROVIDER` setting: `unavailable` selects no provider; `zillapi` requires a key and enables on-demand nearby data. Existing ignored env files need no edits. No provider request occurs during construction, property search, History or pricing. A selected Schools context requests the new subject when the visible property changes.

`GET /api/properties/:id/nearby-schools` replaces `/assigned-schools`, with a dedicated shared `NearbySchoolsResponse` contract. States distinguish `SOURCE_UNAVAILABLE`, `DATA_UNAVAILABLE`, `NO_RESULTS` and `AVAILABLE`; sanitized provider failures remain HTTP errors with fixed codes/request IDs. No API response identifies a nearby school as assigned. The client preserves request cancellation, response validation, property-ID checks and stale-response suppression. UI grouping follows reported school levels; unknown labels remain Other. Attribution and an attendance disclaimer appear beside the display data. No assignment, district, provider school ID or grade is inferred. School IDs are local display identities. Zillapi does not supply a confirmed school-coordinate contract here; the service optionally enriches only its existing schools using `NcesSchoolLocations`. This queries the fixed NCES EDGE 2024–25 public-school layer once by escaped school names and state, with WGS84 output, a 200-record cap, an eight-second deadline and a streaming 256 KiB limit. No subject address or coordinates are transmitted to NCES. Unique normalized name/state matches must also agree with the locally calculated distance (within 0.75 mi or 25% of the provider distance); without provider distance, require matching city and a ten-mile bound. An overall 25-mile bound, ambiguity rejection and truncation rejection prevent broad or arbitrary matches. A terminal School suffix is treated as a name variant. The layer supplies the actual point and NCES identity, not assignment evidence. Private/missing/unmatched schools stay list-only. Failed enrichment preserves all nearby metadata. A separate 32-entry, ten-minute cache and singleflight avoid repeated location queries. The API reports `locationSource: NCES_EDGE_2024_25` for enriched entries; the panel labels the dataset/version. Purple circle graphics, list/marker selection and one-time framing of the subject plus located schools share the existing context layer and MapView. Selection does not repeatedly reset the view.

The client projects `zpid,address,schools` by address first. Missing/null school data plus a numeric ID permit one school-subresource request; an explicit empty list needs no second call. Normalized street/city/state/ZIP and unit identity must match before displaying records or requesting the subresource. Transport uses fixed HTTPS URLs, Bearer auth, a 60-second signal per request (at most two sequential requests, approximately 120 seconds total), no redirects/retries, a streaming 256 KiB limit and Zod validation. Authentication/access, credits, rate limits, not-found, timeout, malformed data and subject mismatch remain distinct sanitized failures. The route inherits the app's local Origin guard and saved-property requirement; it does not accept arbitrary addresses.

Same-subject requests share one in-flight operation, and concurrent other subjects fail busy instead of building a paid queue. The bounded 32-entry, ten-minute memory cache holds address hashes, allowlisted nearby display fields and safe diagnostics, with no raw property records or database persistence. Cache hits make no new calls and failures are not cached. The route sends `Cache-Control: no-store` to keep browser/proxy caching separate from the explicit server cache. Vendor documentation encourages short-lived client caching; licensing/underlying-data rights remain qualified as recorded in [provider findings](provider-capabilities.md#nearby-schools-scope-revision--2026-10-14). No Esri Places data enters this cache. The separately gated diagnostic CLI emits safe metadata only and does not verify attendance eligibility.

`GET /api/properties/:id/nearby-places?category=grocery` requires a saved subject with coordinates. Express uses only the server `ARCGIS_PLACES_API_KEY` to resolve exact Grocery Store and Supermarket category IDs, then calls ArcGIS Places near-point once with bounded radius and page size. It returns a strict display allowlist: ID, name, category, coordinates, approximate distance, and source. Missing credential, rate limit, no results, no coordinates, and provider error are explicit states. The endpoint sends `Cache-Control: no-store`; the client clears the response and graphics on switch or off. No Places result is passed to the property or market repositories, snapshots, logs, fixtures, cache files, or OpenAI. Live Places access and category coverage remain unverified.

## Wildfire and fault context

`GET /api/properties/:id/wildfire-context` and `/fault-context` load a saved subject and perform only on-demand official GIS queries. Both routes return `Cache-Control: no-store`, source/version metadata, checked time, and explicit no-coordinates, no-coverage/no-nearby, and unavailable states. The GIS transport uses fixed official URLs, an eight-second timeout, no redirects or retry, and a bounded JSON response. It does not log or persist raw government features.

The wildfire adapter first intersects the point with CAL FIRE's responsibility-area layer (`SRA`, `LRA`, or `FRA`), then queries the applicable official SRA or LRA Fire Hazard Severity Zone polygon. It returns only Moderate, High, or Very High as a displayed classification. A returned LRA `NonWildland` record is represented as outside the displayed hazard zone; FRA and unknown coverage are reported as no coverage. SRA's 2024 designation is effective; the 2025 LRA layer is a recommendation and does not assert local adoption. A zone is a fire-hazard designation, not an individual property's risk or safety assessment.

The fault adapter queries CGS's 2010 Quaternary Faults polyline layer within 20 miles. It calculates a minimum point-to-segment distance in a local tangent plane, rounds to hundredths of a mile, and returns the nearest mapped name where present. This is not an Alquist-Priolo zone intersection, earthquake probability, structural safety, or insurance conclusion. No hazard or fault field reaches pricing. The client clears the old context response on switching and aborts stale requests, so subject A's result cannot appear under subject B.

## Deterministic pricing preview

`POST /api/properties/:id/pricing/preview` validates an Offer or Listing strategy request. `PricingPreviewService` loads the saved `PropertyEnvelope` and the existing configured `MarketContextResponse`, validates both contracts, and projects only effective subject facts, recorded-sale candidates, active-listing asks, freshness/source metadata, and explicit user settings into the domain input. It never passes Places, schools, wildfire, faults, or OpenAI data. The engine in `shared/src/pricing.ts` is plain deterministic TypeScript, independent of React, Express, Prisma, ArcGIS, and AI. The route sends `Cache-Control: no-store` and does not write an analysis snapshot or `AnalysisRun`.

`ppi-pricing-v1` owns sale eligibility, deduplication, simple distance/recency/size weights, weighted median price per sqft, observed weighted-quantile Market Reference Range, descriptive evidence quality, and distinct Offer/Listing range positions. Every candidate is marked included with factors and final weight or excluded with a reason code. Three eligible sales and positive subject living area are required; insufficiency returns no numeric price. Active asks remain separate competitive context. An Offer budget is a hard ceiling; if it is below the observed range, no offer is suggested. The engine does not broaden the market search. See [pricing engine v1](pricing-engine-v1.md) for exact formulas and thresholds.

## Saved analysis and UI

Dashboard resolves and displays a saved/live profile with source, fetched time, expiry, and stale status. History reads PostgreSQL with address search and pagination, and supports view, notes/override edits, explicit refresh, and confirmed delete. Offer and Listing create or reopen saved `AnalysisRun` versions. Each version stores the normalized pricing input and engine result, explanation and provenance metadata, and a deterministic hash. History opens exact frozen versions. A failed OpenAI explanation leaves its deterministic price visible. The older pricing preview API remains unsaved for deterministic-only callers. Milestone-02 pricing fixtures remain isolated and are not imported into production routes.

OpenAI receives a compact allowlisted projection and returns only structured narrative. The pricing engine remains the sole source of prices; the model output is checked against evidence IDs and engine amounts. Places and GIS context do not enter AI or analysis persistence. See [AI analysis](ai-analysis.md). Verified attendance assignments remain outside the revised nearby-school scope. The provider smoke CLI remains separate from app startup and property resolution.

History uses bounded summary pages, independent latest Offer/Listing summaries, and exact-run reads. An open historical dialog keeps its owning property independently of table refreshes. Analysis requests reuse retry keys, suppress StrictMode duplicate POSTs, cancel obsolete client work, and retain deterministic results if status polling fails. Expired RUNNING rows become INTERRUPTED on claim or read. Map tests verify view reuse, watcher cleanup, contextual geometry clearing, and safe popup text rendering.
